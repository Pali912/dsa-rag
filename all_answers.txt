Q: How do I detect a cycle in a graph?
------------------------------------------------------------
To detect a cycle in a graph, you can perform a depth‑first search (DFS) starting from each node that has no incoming dependencies (or from every node if you’re not sure which are independent).

1. **Start DFS from a node** – mark it as visited and put it on the recursion stack (or keep a separate “currently exploring” set).  
2. **Traverse its neighbors** – for each adjacent node:
   * If the neighbor has not been visited, recursively DFS into it.
   * If the neighbor is already on the recursion stack (i.e., it’s currently being explored), you have encountered a back edge, which means a cycle exists.
3. **Backtrack** – when you finish exploring a node, remove it from the recursion stack.

If any DFS call discovers a back edge, the graph contains a cycle; otherwise, after all nodes are processed, the graph is acyclic. This approach is the standard way to detect cycles in directed graphs, as used in the Course Schedule problem.

Q: What is the sliding window technique used for?
------------------------------------------------------------
The sliding‑window technique is a way to process **contiguous sub‑segments** of a sequence (an array or a string) efficiently.  
You keep a “window” that covers a portion of the data, move it step‑by‑step across the whole input, and update whatever information you need (e.g., the maximum element, the count of a character, the length of a valid substring) as the window slides.  

Because the window is adjusted incrementally—usually with two pointers that expand or shrink it—you avoid recomputing everything from scratch for each position, achieving linear‑time solutions for problems such as:

* Finding the maximum in every window of size K (Sliding Window Maximum).  
* Determining the smallest substring that contains all required characters (Minimum Window Substring).  
* Computing the longest substring that can be turned into all the same character with limited replacements (Longest Repeating Character Replacement).

In short, sliding windows let you solve many “range‑based” problems in O(n) time by maintaining and updating a moving window over the input.

Q: How does the two pointer approach work?
------------------------------------------------------------
The two‑pointer technique uses **two references that move through the data structure at different rates**.

1. **Initialize two pointers** – often called “first” (or slow) and “second” (or fast).  
2. **Create a gap** by moving the second pointer ahead of the first by a fixed number of steps. In the linked‑list example, the second pointer is advanced several nodes before the loop starts.  
3. **Advance both together** – after the gap is set, you move both pointers forward one step at a time, keeping the distance between them constant. You continue this until the second pointer reaches the end condition (e.g., its `next` is `null`).  
4. **Use the positions** – because the second pointer is always ahead, when it hits the end, the first pointer will be at the desired location (such as the node just before the one to delete, or the start of a sliding window).

So, the two‑pointer approach works by **setting a relative offset between two pointers and then moving them in lockstep**, allowing you to locate or process elements based on that offset without extra passes or extra space.

Q: What is dynamic programming and when should I use it?
------------------------------------------------------------
Dynamic programming (DP) is a problem‑solving technique where you break a problem into smaller sub‑problems, solve each sub‑problem once, store (or “memoize”) its result, and then use those stored results to build up the solution to the original, larger problem.  

The key ideas are:

* **Divide into smaller segments** – solve a tiny piece of the problem first.  
* **Reuse results** – keep the answer for each sub‑problem (often in an array) so you don’t recompute it.  
* **Build up** – combine the stored results to obtain the answer for the next larger segment, eventually reaching the full problem.

You should use DP when:

* The problem can be expressed as a recurrence that depends on solutions to smaller, overlapping sub‑problems (e.g., “how many ways to decode a string up to position *i*” or “maximum amount you can rob from the first *i* houses”).  
* Solving the sub‑problems independently would cause a lot of repeated work (the brute‑force approach is exponential).  
* You can store the intermediate results in a table (or just a few variables) to achieve a much lower time complexity, often reducing space to O(1) if you only need the last few values.

In short, whenever you notice that solving a problem involves repeatedly solving the same smaller sub‑problems, dynamic programming is the technique to apply.

Q: What is a greedy algorithm?
------------------------------------------------------------
A greedy algorithm solves a problem by repeatedly making the locally best (or “most promising”) choice at each step, without backtracking, and hopes that this series of optimal local decisions leads to a globally optimal solution.  

- In the coin‑change example, the greedy idea is to always pick the largest‑value coin first because it reduces the remaining amount the most.  
- In the non‑overlapping intervals problem, the greedy step is to keep the interval that finishes earliest, which lets you fit the maximum number of intervals.  
- In the Jump Game, the greedy approach works backward, always extending the reachable range as far as possible.

The key characteristic of a greedy algorithm is that it builds the solution step‑by‑step using the best immediate option, which often yields an efficient solution (e.g., O(n log n) or O(n) time) but must be proven correct for each specific problem.

Q: How does prefix sum help with subarray problems?
------------------------------------------------------------
A prefix sum is just the cumulative total of the array elements as you walk through it.  
Because you keep the running total `pref[i] = a[0] + a[1] + … + a[i‑1]`, the sum of any subarray that starts at index `i` and ends at index `j‑1` can be obtained instantly with one subtraction:

```
sum(i … j‑1) = pref[j] – pref[i]
```

So instead of recomputing the sum for every possible subarray (which is the bottleneck of the brute‑force approach), you compute the prefix sums once in O(n) time and then any subarray sum is retrieved in O(1).  

When you’re looking for subarrays whose sum equals a target `K`, you simply check whether `pref[j] – pref[i] == K`. This can be turned into an even faster solution by storing each `pref` value (or `pref – K`) in a hash map and checking for matches as you scan the array. In short, prefix sums turn repeated subarray‑sum calculations into constant‑time look‑ups, dramatically speeding up subarray problems.

Q: How do I merge k sorted lists?
------------------------------------------------------------
To merge k sorted linked lists you:

1. **Handle trivial cases** – if the array of list heads is empty or null, just return null.

2. **Use a divide‑and‑conquer helper** – pass the whole array together with the start index 0 and the end index (k‑1) to a recursive routine.  
   - The helper splits the range in half, recursively merges the left half and the right half, and then merges the two resulting lists.  
   - This reduces the problem from k lists to merging two lists at each level, giving an overall time of O(N log k) (where N is the total number of nodes) and only O(1) extra space.

3. **Merge two sorted lists** – the core of the helper is the classic two‑list merge:  
   - Create a dummy node and a pointer `curr` that starts at the dummy.  
   - While both list heads are non‑null, compare their values; attach the smaller node to `curr.next` and advance that list’s pointer.  
   - Move `curr` forward, then continue the comparison.  
   - When one list is exhausted, link the remaining part of the other list to `curr.next`.  
   - Return `dummy.next`, which is the head of the merged list

Q: What is the approach for trapping rain water?
------------------------------------------------------------
The approach is to examine each position in the elevation map and compare the tallest bars on its left and right sides.

1. **Find the highest bar to the left** of the current index.  
2. **Find the highest bar to the right** of the current index.  
3. Take the **minimum** of those two heights – that is the highest level water can reach at this position.  
4. Subtract the height of the current building from that minimum.  
   - If the result is positive, it is the amount of water (in unit squares) that can be trapped at that index.  
   - If the result is zero or negative, no water is trapped there.

Repeating this for every index and summing the positive results gives the total units of trapped rain water. This “minimum‑of‑max‑left‑and‑max‑right minus height” rule is the core of the solution.

Q: How do I detect a cycle in a linked list?
------------------------------------------------------------
To detect whether a linked list contains a cycle you can examine the nodes as you walk through the list and look for a repeated node address.

**Method using a hash table (or hash set)**  
1. Start at the head of the list.  
2. For each node you visit, store its memory address (e.g., `0x0015`, `0x0016`, …) in a hash table.  
3. Before inserting a node’s address, check whether that address is already present in the table.  
4. If you ever find an address that is already stored, the list has looped back to a previously‑seen node → a cycle exists.  
5. If you reach the end of the list (`next` is `null`) without finding a duplicate address, the list has no cycle.

Because each node’s address is unique, this approach works even when node values are duplicated—the duplicate values don’t matter, only the duplicate addresses indicate a cycle.
